# 동시 발표 중복 방지

사용자가 대화에서 선택·구현 요청한 범위: DB 락과 회원 Unique 제약으로 같은 지원자의 동시 발표 요청 10개를 회원 1행·알림 요청 1회로 제한한다. 현재 refactor/baseline 브랜치에서 수정하고 커밋한다.

- 원인: 발표 시 publicStatus를 검사하지 않고, 회원 존재 확인과 INSERT 사이의 경합을 DB가 막지 않는다.
- 선택: 지원서 행의 PESSIMISTIC_WRITE 락을 잡은 뒤 publicStatus가 WAIT인 경우만 발표한다. 트랜잭션 종료까지 락이 유지돼 다른 인스턴스의 요청도 기다린다.
- 대안: Java synchronized는 다중 인스턴스에서 충분하지 않다. 조건부 UPDATE도 가능하지만 이번에는 사용자가 선택한 락 방식을 적용한다.
- 여러 지원서를 포함한 요청은 UUID 순서로 잠금을 먼저 획득해 서로 반대 순서의 요청에서도 교착 위험을 줄인다. 처리·검증은 원래 입력 순서를 유지한다.
- 회원 DB 제약: (club_id, profile_id)에 uk_club_member Unique를 추가한다. 기존 DB에는 별도 수동 SQL을 제공한다. 기존 중복 데이터는 임의 삭제하지 않는다.
- 유지: Endpoint·DTO·권한·WAIT 심사 건너뜀·기존 회원 재사용. 이미 발표한 요청은 성공 응답을 유지하고 추가 처리는 하지 않는다.
- 제외: 발표 후 상태 수정 정책, Outbox/재시도, 외부 전송 후 롤백, 정확히 한 번 단말 수신 보장. FCM 호출이 락과 트랜잭션 안에 남는 한계를 기록한다.
- 검증: 동시 요청 10개 × 10회 모두 HTTP 200·회원 1행·FCM 1회, 순차 재요청·본문 중복·DB 직접 중복 INSERT 거절, 반대 순서 배치, 기존 전체 회귀 테스트.
- 기록: 이전 Before 파일을 덮어쓰지 않고 duplicate-publication-fix 폴더에 RED/GREEN 결과를 남긴다. 본인 직접 검증으로 기록하지 않는다.
