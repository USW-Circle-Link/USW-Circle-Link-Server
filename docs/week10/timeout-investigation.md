# 마지막 발표 성능 실험의 타임아웃 조사

2026-11-06 확인. 이전 실패는 삭제하지 않고 보존한다.

## 관측한 사실

1. 2026-11-05 마지막 100명 실험은 21:20:10 시작. 30개 요청 중 29개 HTTP 성공, 마지막 한 건 타임아웃.
2. Windows System 로그 Kernel-Power 506: 21:31:08 Power Button으로 대기 진입, 21:31:09 Lid로 대기 재진입.
3. 21:35:00 일시 복귀·대기 재진입 후 2026-11-06 11:56:48 Lid로 최종 복귀.
4. k6는 21:35:03 마지막 요청 timeout을 기록했고, 21:35:04 관측 종료 API는 활성 연결이 남아 500을 반환했다.
5. 서버 Hikari 로그는 복귀 시점에 약14시간25분의 housekeeper 지연을 기록했다.

Windows 전원 이벤트는 [원본에서 추출한 기록](../../evidence/week10/performance/20261105-203107-2f3a38ac/previous-failure-power-events.json)에 시각·이벤트 ID·RecordId·메시지를 보존했다.

## 판단과 한계

실험 도중 PC의 대기 모드 전환이 실제 발생했다. 따라서 해당 타임아웃을 정상 부하 조건의 서버 성능 한계로 해석하지 않는다. 덮개·전원 버튼으로 인한 실행 중단과 네트워크·스케줄링 지연이 겹친 환경 오염 사례로 분류한다. 이 증거만으로 애플리케이션의 모든 결함을 배제하지는 않으며, 안정된 환경에서 같은 발표를 새 데이터로 재측정한다.

## 재측정 방법

- 이전 결과를 덮어쓰지 않고 100명 조건 전체를 새 캠페인에서 3회 재측정한다. 각 실행 30개 요청·VU1·FCM200ms·별도60초워밍업·Java17·heap1GB·Hikari10 유지.
- 재측정 캠페인은 빈 전용 DB에서 100명 조건만 시작한다. 이전 캠페인은 50명 실행 뒤 100명을 측정했으므로 초기 DB 행 수 차이와 측정 날짜를 결과에 명시한다. 서로 다른 캠페인의 원시값을 하나의 전체 p95로 합치지 않는다.
- 측정 스크립트가 실행되는 동안만 전용 스레드에서 `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED | ES_DISPLAY_REQUIRED)`로 시스템 절전과 화면 꺼짐을 억제하고 finally에서 해당 스레드가 해제한다. 영구 전원 설정·덮개 동작은 변경하지 않는다.
- 이 API는 사용자의 덮개 닫힘·전원 버튼 대기 동작을 차단하지 않는다. [Microsoft 공식 문서](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate).
- 매 실행 동안의 Kernel-Power 대기·복귀 기록을 별도 저장하고 발생 시 정상 비교 실험으로 인정하지 않는다.
- 관측 종료 실패 시에도 DB 검증 완료라고 표시하지 않고 부분 자원·FCM 기록을 보존한다. 활성 요청이 있을 때 이 기록을 저장하는 회귀 테스트를 RED→GREEN으로 확인했다.
- 애플리케이션의 발표·FCM 순차 처리·트랜잭션 로직은 변경하지 않는다. 이번 보완은 측정 환경과 실패 증거 수집에 한정한다.

```powershell
.\scripts\run-publication-benchmark.ps1 -Counts 100
```

## 첫 재측정에서 추가로 확인한 화면 유휴 전환

`20261106-123104-a7710ab4`는100명 정식1회가 정상 완료됐으나, 다음 워밍업 중12:45:14 Kernel-Power506 Idle Timeout을 기록해 중단했다. 워밍업 HTTP3건은 모두 성공했지만 환경 전환이 있어 정상 비교용 전체3회로 채택하지 않았다. 앱 오류로 실패한 것은 아니며 사건을 감지해 도구가 보수적으로 중단한 것이다.

초기 보완은 시스템 요구만 설정해 화면 꺼짐을 막지 않았다. Modern Standby는 화면이 꺼진 뒤 Screen Off와 Sleep 단계로 진행한다. 실제화면유휴 전환을 확인한 뒤 화면 요구도 추가했다. [Microsoft Modern Standby 상태 설명](https://learn.microsoft.com/en-us/windows-hardware/design/device-experiences/modern-standby-states), [시스템·화면 유휴 타이머 설명](https://learn.microsoft.com/en-us/windows/win32/power/system-sleep-criteria).

이 중단 기록과 첫 정상 재측정 결과도 보존한다. 화면 요구·전용 스레드·전원로그 조회 성공 검사를 포함한 새 도구의 소량검증은 `20261106-124828-0c9a28df`에 보관했으며, 전체3회는 새 폴더에서 다시 실행한다.

## 최종 100명 재측정 결과

`20261106-125044-5fb3dc5d`에서 3회 모두 정상 완료했다. 각 30개 신규 발표 요청의 p95는 22440.96ms, 22364.19ms, 22382.58ms이며 총 90개 요청의 실패는 0건이다. 매 회 결과 공개 3000건, PASS 회원 1500행, FCM 대역 호출 3000회가 일치했고 토큰별 누락·중복은 0건이었다.

캠페인 시작 12:50:45부터 마지막 검증 종료 13:28:20까지 System 전원 로그 조회가 성공했고 대기·복귀 사건은 0건이었다. 측정 종료 후 임시 절전 억제 해제도 `awake-released.json`에 기록했다. 이전 실패와 첫 재측정 중단은 삭제하지 않고 별도 이력으로 보존한다.

50명 기준선은 11월 5일의 검증된 3회를 유지하고, 100명은 이번 11월 6일의 새 3회로 구분한다. 날짜·시작 DB 상태가 달라 합친 전체 p95를 만들지 않았다. [최종 기준선 보고](performance-baseline.md).
