# 동시 발표 중복 방지 수정 기록

작업일: 2026-11-05. 기준 커밋: `6ea024fb7c5df0986c0d3af341544844f28a2a36`.
브랜치: `refactor/baseline`. AI가 수정·실행했으며 사용자의 직접 검증 기록과 구분한다.

## 무엇을 바꿨는가

1. **지원서를 먼저 잠근다.** DB의 `PESSIMISTIC_WRITE` 락으로 다른 발표 요청이 같은 지원서를 동시에 처리하지 못하게 한다. 잠금은 트랜잭션 종료까지 유지된다.
2. **잠근 뒤 발표 여부를 확인한다.** `publicStatus`가 WAIT가 아니면 성공 응답은 유지하되 회원 생성과 알림 전송을 건너뛴다. 심사 결과가 WAIT인 지원자는 기존처럼 처리하지 않는다.
3. **DB에도 중복 저장 방지 제약을 넣는다.** `uk_club_member (club_id, profile_id)`로 같은 동아리·같은 사람의 회원 행을 두 번 저장하지 못하게 한다. 다른 동아리 가입은 가능하다.

다건 요청은 UUID 순으로 락을 획득한다. 입력 순서가 반대인 요청끼리 서로 다른 지원서를 하나씩 잡고 기다리는 교착 위험을 줄이기 위한 순서다. 실제 발표·오류 처리는 기존 입력 순서를 유지한다.

## 기존 DB 적용

엔티티 제약은 새로 생성한 테스트 DB에서 검증했다. 운영 프로필은 `ddl-auto: none`이므로 **코드 배포만으로 기존 DB에 인덱스가 추가되지는 않는다.**

[수동 적용 SQL](../../scripts/sql/20261105_add_club_member_unique.sql)의 SHOW CREATE TABLE/인덱스 조회와 중복 조회를 먼저 수행한다. 실제 테이블·컬럼 이름과 대소문자를 확인한다. 중복이 있으면 참조 관계와 보존할 행을 확인한 후 별도 정리해야 한다. 이 작업에서는 운영 DB에 접속하거나 기존 데이터를 삭제하지 않았다. 중복이 없고 동등 제약이 아직 없을 때 ALTER를 별도로 적용한다.

## 아직 해결하지 않은 문제

- FCM 호출은 여전히 트랜잭션·락 안에 있어 외부 지연 동안 대기할 수 있다.
- 앞선 알림 전송 후 뒤에서 실패해 DB가 롤백되면 다음 요청이 다시 알림을 보낼 수 있다. 이번 변경은 성공적으로 커밋된 발표의 중복 요청을 막으며 정확히 한 번 단말 수신을 보장하지 않는다.
- 토큰 없음/인증 IOException 등 기존 실패 처리, 발표 후 상태 수정 정책, 다른 쓰기 경로의 Unique 위반 응답 정리는 후속 작업이다.
- 부하 성능 측정은 아직 하지 않았다.
