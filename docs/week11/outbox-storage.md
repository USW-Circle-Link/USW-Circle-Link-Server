# 11주차 Outbox 저장 구조

## 이번 작업의 의미

Outbox는 나중에 보낼 알림을 DB에 보관하는 대기함이다. 이번 단계에서는 테이블·Entity·Repository와 저장 테스트만 추가한다. 발표 API에서 아직 이 테이블을 사용하지 않으며 기존 FCM 전송도 바꾸지 않는다. 비동기 처리 완료나 성능 개선으로 보고하지 않는다.

브랜치: `refactor/publication-outbox`. 기준 커밋: `6be97523`. 기존 Word 및 테스트 변경은 보존하며 이번 커밋에 섞지 않는다.

## 데이터 정책

- `notification_outbox`의 `(application_uuid, event_type)`를 고유 키로 설정한다. 지원서 하나의 결과 발표 작업은 한 번만 저장할 수 있다. 서로 다른 지원서는 같은 수신자여도 별도 작업이다.
- 발표 결과는 PASS·FAIL만 허용한다. WAIT는 작업을 만들지 않는다. 수신자·토큰·결과·제목·본문은 생성 당시 값으로 보관한다.
- 유효 토큰이면 PENDING·시도 횟수0·다음 시도 시각은 생성 시각이다. 토큰이 없거나 공백이면 SKIPPED·NO_FCM_TOKEN이며 재시도 시각은 없다.
- 시각은 Java Instant로 표현하고 MySQL TIMESTAMP(6)에 저장한다. 토큰·프로필 ID는 작업 처리를 위한 데이터이며 보고서나 일반 로그에 노출하지 않는다.
- 지원서 및 프로필에 삭제 연동 FK는 두지 않는다. 원본 데이터 삭제가 작업을 자동 삭제하지 않도록 스냅샷 ID로 보관한다. 보관 기간과 삭제 정책은 실제 작업자 운영 전에 별도로 정한다.
- 저장 API는 새로운 트랜잭션을 강제로 열지 않는다. 호출 서비스의 기존 트랜잭션에 참여한다. 실제 발표 결과·회원과의 전체 롤백 검증은 서비스 연결 단계에서 수행한다.
- SENT·재시도 상태 전환·작업자·임대 잠금은 다음 단계다. 현재 DDL의 상태 CHECK도 작업자를 추가할 때 확장해야 한다.

## SQL 적용

`scripts/sql/20261110_create_notification_outbox.sql`은 MySQL8.0용 명시적 테이블 생성 SQL이다. 운영은 ddl-auto:none이므로 코드 배포 전 별도 적용이 필요하다. 이번 작업은 운영 DB에 접속하거나 SQL을 적용하지 않는다. 테이블이 이미 있으면 오류를 내며, 기존 테이블을 조용히 무시하지 않는다.

## 검증 방법

Docker Desktop Linux 엔진을 켜고 저장소를 W:로 매핑한 상태에서 PowerShell7로 실행한다.

```powershell
.\scripts\run-outbox-storage-tests.ps1
```

전용 `circle-week11-outbox-mysql` 컨테이너·`outbox_week11` DB만 사용한다. 실행 전 컨테이너 이미지·DB명·전용 비밀번호를 확인하고 그 DB의 Outbox 테이블만 초기화한다. 기존 개발·성능 DB는 사용하지 않는다.

테스트는 제공 DDL로 테이블을 만든 다음 Hibernate validate로 Entity와 비교한다. 생성은 Hibernate create-drop에 맡기지 않는다.

| 검사 | 확인할 결과 |
|---|---|
| 정상 저장·재조회 | 스냅샷·PENDING·생성 시각·시도 횟수 보존 |
| 같은 지원서 결과 작업 중복 | DB 고유 키가 두 번째 저장 거절, 기존1건 유지 |
| 같은 수신자의 다른 지원서 | 별도2건 저장 |
| null·빈 문자열·공백 토큰 | SKIPPED·NO_FCM_TOKEN |
| WAIT 작업 생성 | 생성 거절·저장0건 |
| 호출 트랜잭션에서 flush 후 예외 | 새 트랜잭션 조회 시 저장0건 |

실행 결과는 `evidence/week11/outbox-storage`에 남긴다. 실행자는 AI/본인을 구분한다. 테스트 DB의 작업은 실제 알림이 아니다.
