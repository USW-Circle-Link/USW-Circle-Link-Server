# Outbox 작업자와 재시도 구현 계획

기준: `07774727`, 브랜치 `refactor/publication-outbox`. Kafka와 운영 배포는 제외한다. 기존 사용자 수정 파일은 보존한다.

## 결정

- DB polling 방식으로 작업1건을 짧은 트랜잭션에서 선점하고, 커밋 후 FCM을 호출한 뒤 별도 짧은 트랜잭션으로 결과를 기록한다.
- MySQL SKIP LOCKED와 작업별 임대 토큰·30초 임대로 다중 작업자의 동시 처리를 제어한다. 임대가 만료된 PROCESSING 작업은 재선점할 수 있다. 이전 소유자의 늦은 완료는 무시한다.
- 상태를 PENDING, PROCESSING, RETRY, SENT, FAILED, SKIPPED로 확장한다. 기존 생성 SQL은 보존하고 ALTER SQL을 추가한다. sent_at, lease_until, claim_token과 조회 인덱스를 추가한다.
- 최대5회, 기본 재시도2·4·8·16초. 429·5xx·인증 실패·연결/응답 오류는 재시도, 400·404 등 나머지4xx는 영구 실패다. Retry-After가 있으면 기본 간격보다 일찍 재시도하지 않는다. 유효한 헤더는 최대1일 범위로 해석하고 비정상 값은 기본 간격을 사용한다.
- HTTP 연결2초·응답5초 제한. HTTP오류 본문·토큰·키 파일은 로그/Evidence에 남기지 않는다. 기존 FCM 전송 코드는 바꾸지 않고 Outbox 전용 전송기를 추가한다.
- 작업자는 기본 비활성화이며 outbox-test 프로필에서 명시적으로 활성화할 때만 실행한다. 1초 간격으로 최대10건을 한 건씩 선점한다. 작업자 활성화에는 Outbox 발표 모드도 필요하다.
- SENT는 FCM HTTP 접수 성공이며 실제 휴대폰 수신이 아니다. 외부 성공 후 DB 완료 기록 전 중단 경계에서는 재전송될 수 있는 at-least-once 한계를 문서화한다.

## 구현 순서

1. 실패하는 테스트 작성: 실제 MySQL에서 작업 선점·성공·재시도·영구 실패·임대 복구·동시 선점·늦은 완료 무시·전송 중 DB 연결 반환을 검사한다.
2. Entity/DDL 확장, 선점·완료 저장소, FCM 전송기, 작업자·조건부 스케줄러 구현.
3. WireMock으로200·500두번후200·429 Retry-After·400·404·연결단절·응답지연과 가짜 인증 IOException을 검사한다. 시간을 직접 제어하는 Clock으로 재시도 정책을 빠르게 검증한다.
4. 발표 API→Outbox→작업자→WireMock→SENT의 통합 흐름 검사. 실제 Firebase/Google/S3/메일은 호출하지 않는다.
5. 이전 저장·발표 연결·동기 경로 회귀 및 bootJar 확인. 요청·상태·시도 횟수·FCM 호출 수·처리 시간을 Evidence로 보관한다.
6. 독립 읽기 전용 리뷰 후 예정 메시지로 커밋한다. API 성능 개선 수치는 별도 부하 재측정 전 주장하지 않는다.
